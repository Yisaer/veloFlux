# API Docs

## Trust and deployment model

VeloFlux is designed for a single trust domain on a private LAN. All management
API callers are trusted administrators authorized to control the engine and use
its server-side file access capabilities. The API does not provide a security
boundary between tenants or between administrators and less-trusted users.

Authentication, authorization, and protection of API access are responsibilities
of the deployment environment and are outside the scope of the open-source
engine. Operators must restrict API access to trusted administrators, for example
through network access controls or an authenticating gateway. Being on a LAN
alone does not establish that a caller is trusted; do not expose the API to
untrusted clients or directly to the public Internet.

Where an API accepts a server-local file path, access uses the VeloFlux process's
filesystem identity and permissions. An absolute path refers to the server's
filesystem, including its container filesystem when containerized, rather than
the caller's machine. Operators define the accessible files through the service
account, filesystem permissions, container mounts, or OS access controls. Do not
assume a general sandbox restricting these APIs to the data directory.

Individual endpoint constraints still apply. In particular, the file upload API
accepts validated names within the uploads directory; permission to reference a
server-local file does not permit upload names or archive entries to escape
their designated directories.

## Server-local resource file paths

Relative server-local file paths in resource definitions are resolved against
`data_dir`, not the process working directory. Absolute paths are used as given,
subject to the service process's filesystem permissions. Relative paths must not
contain `..` components; use an absolute path to explicitly reference external
files. This rule defines path interpretation, not a filesystem sandbox.

This applies to schema installation `proto_path` / `schema_path`, file stream
`props.path`, file and video sink `props.path`, Kura sink `props.mapping_path`,
and Kuksa sink `props.vss_path`. URLs, resource IDs, upload names, and archive
entry names retain their own contracts.

For example, with `data_dir=/var/lib/veloflux`, uploading
`name=proto/sensor.zip` makes the file available at
`/var/lib/veloflux/uploads/proto/sensor.zip`. A schema creation request references
it as `uploads/proto/sensor.zip`. A file sink `props.path=output` writes under
`/var/lib/veloflux/output`.

Stream and pipeline definitions retain the original paths in persistent metadata
and exports. File stream describe responses also preserve the stored props,
including relative paths and omitted defaults, for revision-safe updates.
The manager resolves paths when constructing runtime resources,
including startup hydration, Import, and Apply. Schema installation consumes its
source ZIP and persists the managed entry instead; it does not depend on the ZIP
after installation. Internal temporary and managed paths are generated by their
owning modules and are not interpreted as user resource paths.

CLI startup paths such as `--config`, `--data-dir`, and `--init-dir` keep their
existing interpretation relative to the startup working directory. The manager
does not change the process working directory. Relative resource paths that
previously relied on that directory must be changed to data-directory-relative
paths or explicit absolute paths.
